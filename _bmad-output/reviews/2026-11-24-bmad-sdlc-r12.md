## Findings

IDs match the findings JSON. `[reproduced]` means the reviewer ran the command or read the code path and observed the described behavior.

### 1. Contract contradictions the model must guess between

These are the highest-value items: each one is a place where two authority files say different things, so the outcome depends on load order.

- **R12-02** `[reproduced]` Headless field set is defined twice with opposite rules — omit the per-level lists (`headless.md:29`) vs emit the unfiltered summary lists (`SKILL.md:110,115`). Four graded runs emitted all three lists and ticket detail.
- **R12-03** `[reproduced]` `blocked_by` is "gate ids" in prose, an action id in its own example (`["build.review"]`), and an action in `headless.md` and the eval.
- **R12-04** `[reproduced]` "the gate id doubles as the action id" is false for the example it gives (`plan.requirements` → `frame.spec`/`plan.prd`). Ownership is still right by prefix; the action lookup is not.
- **R12-05** `[reproduced]` No DEV → QA row for the per-ticket handoff between `build.ticket` and `build.review`, while `phase_roles.build = dev` makes `role_allowed` false there. The only DEV → QA row requires QA's own `build.done`.
- **R12-06** `[reproduced]` The cross-role marker says a foreign phase "offers a handoff ... and never runs a foreign action", but Build is where QA's `build.review`/`build.done` live.
- **R12-12** `[reproduced]` `role --clear` is accepted on a paused workstream; the schema says paused refuses writes.
- **R12-13** `[reproduced]` `build.auto`/`build.loop` advertise `build.ticket` as their gate but are not gate actions and never appear in `summary`.
- **R12-01** `[reproduced]` `summary` has no `role` for the 11 gateless actions, though `SKILL.md` tells the model to filter the menu by "each action's `role` field from `summary`".

### 2. Ownership integrity (separation of duties)

- **R12-14** `[reproduced]` `verify-return` checks that the returned role matches `--expect-role` but not that the role owns the action; the role suite enshrines `qa` + `build.ticket` as accepted.
- **R12-15** `[reproduced]` Self-approval is possible: gate ownership is checked against the gate's owner, not the ticket's builder, and the actor is logged only to the memlog. One DEV session can write `ticket`, `review`, `done` with `--as dev --reason`, and no artifact lets `validate` prove it.
- **R12-16** `[reproduced]` The write that triggers a role transition, `set phases.<p>.status done`, is the one write with no actor check and no reason requirement.
- **R12-11** `[reproduced]` An unknown `role_override` passes `validate` and silently makes `role_allowed` false everywhere.
- **R12-18** `[reproduced]` `DEFAULT_ROLE_CONFIG` silently takes over when `references/role-config.toml` is absent, so "single source of truth" has a runtime fallback.
- **R12-09** `[reproduced]` `roles.*.name` and `roles.*.references` validate but are never read; step 9 hardcodes the overlay paths.
- **R12-10** `[reproduced]` The role enum is hardcoded `pm|dev|qa` in the description and step 4, while validity comes from `[roles]`.
- **R12-17** `[reproduced]` `workstreams_detail[].next_action` is the raw dict without `role`/`role_allowed`, so a missing field reads as "not blocked" in the dashboard.

### 3. Isolation and eval hygiene

- **R12-07** `[reproduced]` "Never write or probe outside `{project-root}`" is contradicted by activation steps 1 and 9. Empirically, three runs routed through `{skill-root}/..` to find `_bmad/scripts`, which the same guardrail forbids. Fix both halves: scope the rule, and state that a missing resolver means reading `{skill-root}/customize.toml` in place.
- **R12-08** `[reproduced]` The eval guardrail names `case.json`/`prompt.txt` (this repo has `cases.json`) and bans "any search whose results include `evals/`", which the harness symlink makes unavoidable. Graders disagreed: one run's skill-root `ls` printed `evals` and passed, another's `find .agents` was called a violation.

## What the eval run says about the eval suite

Worth acting on alongside the skill fixes: the suite is strong where it checks state (gate statuses, ledger contents, writes) and weak where it checks text. Eight of fourteen graders independently flagged the same three blind spots — no memlog assertion, no `assumptions` check, and no headless key-set check — and one flagged that a rubric item claiming "no gate passed" is literally false against its own staged fixture. The single most useful upgrade is to assert the emitted block against the captured `summary` key-by-key, which would have caught R12-02 in every headless case.
